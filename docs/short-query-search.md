# 1〜2文字クエリの検索方式（調査と設計）

日本語の用例検索で「月」「夜」「こと」のような1〜2文字が引けないのは機能の欠落です。
このドキュメントは、その解消方法を実測にもとづいて比較し、採用案と移行手順をまとめたものです。

要件そのものは [テスト仕様書 §9](./test-spec.md#9-短いクエリ12文字) にあります。

---

## 1. 現状と原因

現行のインデックスは FTS5 の `trigram` トークナイザーです。3文字の重なり窓でトークン化するため、
**3文字未満の入力ではトークンが1つも生成されず**、クエリは常に0件になります。
`app/api/search/route.ts` の `MIN_QUERY_LENGTH = 3` は、この制約をユーザーに説明するためのものです。

回避策として検討されがちな2つは、実測の結果いずれも使えませんでした。

| 試したこと | 結果 |
|---|---|
| プレフィックスクエリ `月*` / `"月が" *` | **0件**。トークナイザーはクエリ側でも3文字未満でトークンを出さないため、プレフィックス検索にも乗らない |
| `prefix='1,2'` オプション | 効果なし。プレフィックス索引はトークン（＝3文字）の先頭を索引するもので、クエリ側のトークン化は変わらない |
| `text LIKE '%月%'` | **結果は正しい**が実行計画は `SCAN chunks VIRTUAL TABLE INDEX 0:L0`（全走査） |

## 2. 測定環境

| 項目 | 値 |
|---|---|
| コーパス | 青空文庫の先頭400作品（目録全体は 18,567 作品 = **46.4倍**） |
| 規模 | 8,360チャンク / 2,471,265文字 / 平均296文字per チャンク |
| 現行DB | 33.1MB（`chunks_data` 17.7MB + `chunks_content` 8.7MB） |
| 実行 | `@libsql/client` のローカルファイルDB、SQLite 3.45.1、ウォーム状態 |

本番は Turso（ネットワーク越し）なので、以下のミリ秒値には往復時間が加算されます。
逆に言えば、**1クエリあたりの読み取り行数を小さく保てるか**が本番での実効性能を決めます。

## 3. 候補の比較

### 案A: 現行維持 + `fts5vocab` でクエリを展開

trigram の語彙表（`CREATE VIRTUAL TABLE chunks_vocab USING fts5vocab(chunks,'row')`）は
term 順にソートされているため、`term >= '月が' AND term < '月が￿'` の範囲スキャンで
「月が」で始まる3-gram をすべて列挙できます。それを `OR` で繋いで MATCH に渡します。

実測（400作品）:

| クエリ | 展開語数 | 語彙スキャン | `LIMIT 21` | 全件count |
|---|---|---|---|---|
| `月が` | 19 | 1.0ms | 0.2ms | 0.2ms（36件） |
| `こと` | 120 | 0.6ms | 0.6ms | 1.4ms（3,100件） |
| `夜の` | 101 | 0.4ms | 0.4ms | 0.4ms（209件） |
| `の`（1文字） | **22,948** | **77.8ms** | — | — |

- **2文字なら実用的**。追加インデックス0バイト、再インデックス不要という強みがある。
- **1文字で破綻する**。1文字は「その文字で始まる3-gram 全部」＝数万語の `OR` になり、
  全件コーパスでは語彙が数倍に増える。クエリ文字列も数百KBになる。
- 取りこぼしは「チャンク末尾2文字以内の出現」のみ（3-gram を構成できない位置）。

### 案B: `LIKE '%X%'` の全走査 + 早期終了

`LIMIT 21` を付ければ SQLite は21件見つけた時点で走査を止めます。

| クエリ | `LIMIT 21` | 全件count |
|---|---|---|
| `の`（7,995件ヒット） | 0.3ms | 6.6ms |
| `々`（2,401件） | 0.3ms | 10.5ms |
| `鵺`（**0件**） | **12.0ms** | 11.9ms |

- 頻出語ほど速く、**希少語・0件語で必ず全走査**という性能特性。全件コーパス（46倍）では
  1回あたり0.5秒前後、Turso では全チャンクの転送と行読み取り課金が発生する。
- インデックス追加0バイトなので、フォールバックとしては候補に残る。単独では不可。

### 案C: 1〜2文字の転置表（通常のSQLiteテーブル）

`gram_postings(gram TEXT, chunk_id INTEGER, PRIMARY KEY(gram, chunk_id)) WITHOUT ROWID`。

実測した出現数（400作品）:

| | 異なり数 | ポスティング数 | チャンクあたり |
|---|---|---|---|
| 1-gram | 4,983 | 947,585 | 113 |
| 2-gram | 149,346 | 1,959,941 | 234 |

全件コーパスでは 1-gram 4,400万行 / 2-gram 9,100万行。B-tree の行あたり10バイト前後として
**1.3GB 超**で、既存DBと同規模の追加になります。gram ごとに上限N件へ間引けば
（cap=200 で1-gram 305,041行 / 2-gram 1,327,973行＝全体の68%まで縮む）現実的なサイズに収まりますが、
**その時点で「全件から探す」ではなく「代表例プールから見せる」検索**になり、
ページングも打ち切られます。用例検索としては割り切れなくはないものの、次の案Eが同等以下のコストで
完全な再現率を出せるため採用しません。

### 案D: Roaring Bitmap

案Cのポスティングリストをビットマップで持つ案。1文字あたりのチャンク集合を圧縮して保持します。

- サイズは有利。全件38.8万チャンクなら密な文字は 48.5KB/文字（1bit×チャンク数）で、
  頻出100文字ぶんでも約5MB。1-gram 層の合計はおおむね **40〜60MB** と見積もれます
  （後述の案Eが同じ層に約240MB使うので、**圧縮率では Roaring が勝つ**）。
- ただし決定的な難点が3つあります。
  1. **位置情報を捨てる**ので、2文字以上は「AND した候補を本文照合で検証」する二段構えが必要。
  2. SQLite 側に集合演算がなく、BLOBをアプリに転送してデコードする実装が要る（Turso 越しでは毎クエリ転送）。
  3. 実装・運用コストが FTS5 の doclist（すでに delta+varint 圧縮されたポスティングリスト）に対して割に合わない。
- **結論**: 独立した案としては採らない。案Eの1文字層（約240MB）が容量問題になった場合の
  差し替え先としては有効なので、選択肢として記録しておく。

### 案E: bigram インデックスへの置き換え（**推奨**）

FTS5 にバイグラムのトークナイザーはなく、Turso では拡張のロードもできません。そこで
**インデックス投入時にアプリ側で2-gram へ展開**し、標準の `unicode61` で索引します。

```
本文:   月 が 綺 麗
トークン: "0067083044" "003044007dba" "007dba9e97" ...   ← コードポイント6桁hex × 2
```

- **hex 符号化する理由**: 生の文字を空白区切りで並べると、`、` `。` `「` などの記号を
  `unicode61` がセパレータとして落としてしまい、記号をまたぐ検索が壊れる。
  コードポイントの16進表記なら常に英数字トークンになり、サロゲートペアも6桁固定で扱える。
- **番兵**: 末尾に1コードポイント（`\n`。本文からは `cleanAozoraText` が除去済み）を足して
  2-gram を作る。これがないと「チャンク末尾の1文字」だけ取りこぼす（実測で確認済み: `ぬ` が1件欠けた）。
- **クエリ変換**: 1文字は `hex(cp)*` のプレフィックスクエリ、2文字以上は2-gram列のフレーズクエリ。
  重なり2-gram のフレーズ一致は部分文字列一致と厳密に等価（偽陽性・偽陰性なし）。
- **`prefix='6'`**: 6桁＝1文字ぶんのプレフィックス索引を FTS5 に作らせる。これが実質のユニグラム索引。
- **`content=''`（contentless）**: 展開後の文字列は保存しない。本文は通常テーブルに置き、
  スニペットはアプリ側で生成する。

実測（400作品）:

| 構成 | `bi_data` | DBファイル |
|---|---|---|
| bigram（prefix索引なし） | 9.1MB | 14.4MB |
| bigram + `prefix='6'` | 14.2MB | 19.6MB |
| bigram + `prefix='6'` + 本文テーブル | 14.2 + 8.6MB | 28.3MB |
| （比較）現行 trigram | 17.7MB | 33.1MB |

| クエリ | rowid順 `LIMIT 21` | `ORDER BY rank` | 全件count | 現行trigram |
|---|---|---|---|---|
| `の`（7,995件） | **0.2ms** | 10.8ms | 0.8ms | 検索不可 |
| `月`（1,160件） | 0.1ms | 1.4ms | 0.1ms | 検索不可 |
| `鵺`（0件） | 0.1ms | 0.0ms | 0.1ms | 検索不可 |
| `月が`（36件） | 0.1ms | 0.2ms | 0.1ms | 検索不可 |
| `人間の心`（11件） | 0.17ms | — | 0.1ms | 0.29ms |
| `ということ`（132件） | 0.30ms | — | 0.2ms | 0.80ms |

- **prefix索引の有無で1文字クエリが 16.2ms → 0.2ms**。5MB（全件推定240MB）の投資で桁が2つ変わる。
- 3文字以上でも現行 trigram と同等以上（件数も完全一致）。**trigram を置き換えられる**。
- `ORDER BY rank` は1文字クエリでポスティングリストを全走査する（`の` で10.8ms、全件推定0.5秒）。
  **短いクエリでは rank を使わない**設計にする（→ §4）。

**完全性の検証**: コーパスから無作為抽出した部分文字列（1・2・3・4・7文字 × 各60件、計300件）について、
bigram インデックスの件数と `LIKE '%…%'` の件数を突き合わせ、**300件すべて一致**（番兵導入後）。

### 案F: FM-index（BWT + wavelet tree）

理論的にはこの問題の本命です。任意長のパターンを O(|P|) で後方検索でき、
**1文字でも厳密な出現件数が SA 区間の幅として即座に得られます**。

- 全件コーパスは UTF-8 で約345MB。バイト単位 BWT + wavelet tree（rank 構造込み）と
  SA サンプル（間隔32）で、**常駐 250〜350MB** 程度。案Eの推定1.06GB より小さい。
- 一方で本プロジェクトの構成には載りません。
  - **常駐プロセスが必須**。Vercel の関数はコールドスタートのたびに数百MBをロードできず、
    Turso（SQL）からも使えない。検索を別サービス（Fly.io など）に切り出す前提の技術。
  - 更新は**全再構築**（青空文庫は追加更新があるため、月次バッチなら許容範囲ではある）。
  - グローバル位置 → チャンクID の変換に、チャンク境界の配列と二分探索が別途必要。
- **結論**: 今回は見送り。ただし「検索を独立サービスにする」判断をするなら第一候補で、
  そのときは案Eのアプリ側ロジック（正規化・クエリ変換・スニペット生成）をそのまま流用できる。

### 参考: 採らなかったその他

| 案 | 見送りの理由 |
|---|---|
| 形態素解析（MeCab / Vibrato）索引 | 用例検索の要件は任意部分文字列一致。語境界に依存する索引だけでは満たせない。ランキング改善の材料としては有用 |
| PostgreSQL `pg_bigm` | 要件はほぼ満たす（2-gram索引・1文字は部分再現）が、DB を Turso から移す判断が伴う |
| Groonga / Elasticsearch（ngram） | 同上。運用対象が1つ増える。現状の「Next.js + Turso だけ」という構成の単純さを失う |

## 4. 採用案の設計（案E）

### スキーマ

```sql
CREATE TABLE chunks (              -- 本文（表示とスニペット生成に使う）
  id      INTEGER PRIMARY KEY,
  work_id INTEGER NOT NULL,
  text    TEXT NOT NULL
);
CREATE VIRTUAL TABLE chunks_fts USING fts5(
  t,
  prefix  = '6',                   -- 1文字ぶんのプレフィックス索引 = ユニグラム索引
  content = '',                    -- contentless（展開後の文字列は保存しない）
  tokenize = 'unicode61'
);
```

`chunks_fts.rowid` は `chunks.id` と一致させる。

### インデックス投入

```ts
const SENTINEL = 0x0a;
const hex = (cp: number) => cp.toString(16).padStart(6, '0');

function bigramTokens(text: string): string {
  const cps = [...text].map((ch) => ch.codePointAt(0)!).concat(SENTINEL);
  const out: string[] = [];
  for (let i = 0; i + 1 < cps.length; i++) out.push(hex(cps[i]) + hex(cps[i + 1]));
  return out.join(' ');
}
```

### クエリ変換

```ts
function matchExpr(q: string): string {
  const cps = [...q].map((ch) => ch.codePointAt(0)!);
  if (cps.length === 1) return hex(cps[0]) + '*';                 // 1文字 → プレフィックス
  const grams: string[] = [];
  for (let i = 0; i + 1 < cps.length; i++) grams.push(hex(cps[i]) + hex(cps[i + 1]));
  return `"${grams.join(' ')}"`;                                  // 2文字以上 → フレーズ
}
```

FTS5 の演算子（`*` `OR` `AND` `"`）は hex に符号化された時点で消えるため、
現行の「クエリを引用符で囲んでリテラル化する」処理（DB-13 / DB-14）は不要になります。
**符号化そのものがエスケープを兼ねます**。

### スニペット

contentless FTS5 では `snippet()` / `highlight()` が使えず、hex トークンの位置は本文の文字位置とも
一致しないため、**アプリ側で生成**します。本文と検索語がわかっていれば `indexOf` と前後の切り出しで足り、
副次的に「HTMLエスケープしてから `<mark>` を付ける」ことが可能になります
（現在テスト仕様書 §10 で「対象外」としている問題が消える）。

### 並び順

- 短いクエリで `ORDER BY rank`（bm25）を使うと全ポスティング走査になるため使わない。
- **rowid 昇順**（＝ 作品ID順）で返す。ページングが安定し、`LIMIT`/`OFFSET` がそのまま使える。
- 反面、結果が同じ作品に固まりやすい。「作品ごとに最大N件」といった多様化は別課題として残す
  （テスト仕様書 SQ-10 に要件だけ置いてある）。

### 正規化

- 現行の trigram は既定で英字の大小を同一視するため、**符号化前に小文字化**して挙動を揃える。
- 全角・半角の同一視（NFKC）は今回のスコープ外。NFKC は文字数を変える変換（`㍿` → `株式会社`）を
  含み、スニペットの位置合わせに影響するため、やるなら本文側も正規化して保存する判断が要る。

## 5. 移行計画

| 段階 | 内容 | 本番への影響 |
|---|---|---|
| 1 | テスト仕様書 §9 と `tests/short-query.test.ts`（`it.skip`）を入れる ← **このPR** | なし |
| 2 | `scripts/build-index.ts` を新スキーマに、`lib/db.ts` に新旧スキーマの判定を追加（`hasAuthorUrl` と同じ検出パターン）。テストの `.skip` を外す | なし（旧DBのままなら旧経路で動作） |
| 3 | Reindex ワークフローで新DBを構築し、Vercel の環境変数を切り替え | 切り替え時点で1〜2文字が有効になる |
| 4 | `MIN_QUERY_LENGTH` を 1 に、`app/page.tsx` の自動検索しきい値も 1 に | — |
| 5 | 旧DBを `turso db destroy` | — |

段階2で新旧を両方サポートするのは、Reindex が別名DBを作る運用（README 参照）のためです。
切り替えるまで本番は旧DBを見るので、コードだけ先に出せます。

## 6. 残るリスク

| リスク | 見立て |
|---|---|
| 再インデックス必須（20〜60分） | Reindex ワークフローで実行できる。旧DBは残るのでロールバック可 |
| 投入時の書き込み量が増える | 本文3バイト/文字に対しトークン列は13バイト/文字。contentless なので**保存はされない**が、Turso への送信量は約4.3倍。ローカル構築 → `turso db import` の現行フローなら影響はビルド時間のみ（8,360チャンクのトークン化と投入で2.6秒） |
| 1文字クエリの結果が作品順に偏る | 多様化は未解決（SQ-10）。まずは「引ける」ことを優先 |
| `の` のような超高頻度語の全件件数 | 実測0.8ms（全件推定40ms）。現行の `over_limit`（「N件以上」表示）を維持すれば取得自体が不要 |
| インデックスサイズ | 全件推定1.06GB（現行1.5GBより小さい）。内訳は bigram 660MB + 本文 400MB |

## 付録: 測定の再現手順

```bash
npx tsx scripts/build-index.ts --limit 400     # DB_PATH=data/bench.db
# 語彙展開（案A）と LIKE 走査（案B）の測定、bigram インデックスの構築と検証は
# 本ドキュメント §3 のクエリをそのまま実行して確認できる。
```

数値はすべて 400作品／8,360チャンクでの実測です。全件コーパスの推定値には
「作品数46.4倍・ポスティング数は線形」という仮定を置いています（語彙の増加は劣線形なので、
インデックスサイズは推定より小さく出る見込みです）。
