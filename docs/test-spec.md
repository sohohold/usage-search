# テスト仕様書（青空用例検索）

このプロジェクトをテスト駆動で進めるための仕様書。
**この表が仕様の一次資料**であり、テストコードは表の1行＝1テストケースとして機械的に書き起こす。
実装がこの表と食い違う場合、原則として直すのは実装側。

採用した項目は `tests/` 以下に実装済みで、`npm test` で全件が緑になる状態です。
テスト名の先頭には項目 ID を入れてあるので、失敗したテストから該当行を引けます。

## 進め方

1. 仕様書（この文書）に表を書く
2. 項目の採否を確認する（`採否` 列を ○ / △ / × で確定）
3. 採用項目をテストとして実装し、落ちたテストに合わせてコードを修正する
4. 仕様が変わったらまずこの表を直し、それからテスト・実装を直す

`現状` 列の凡例:

| 記号 | 意味 |
|---|---|
| ✅ | 仕様どおりに動作し、テストで担保されている |
| ❌ | 仕様と食い違っていた項目（テストが赤くなり、実装を修正した） |
| × | 今回は採用しない（理由を備考に記載） |

## 1. テスト構成

| 項目 | 方針 |
|---|---|
| ランナー | Vitest（TypeScript/ESM をそのまま実行でき、`tsx` と同じ前提で動く） |
| 実行環境 | 既定は `node`。React コンポーネントのテストのみ `jsdom` |
| DOM テスト | `@testing-library/react` + `@testing-library/user-event` + `@testing-library/jest-dom`。`app/page.tsx` はフェイクタイマーと相性を取るため `fireEvent` を使う |
| DB テスト | モックせず、一時ファイル上に本物の SQLite + FTS5(trigram) を作って検証する。`snippet()` や `MATCH` の挙動こそ検証対象のため、モックでは意味がない |
| API テスト | Route Handler を直接 `import` し、`NextRequest` を渡して `Response` を検証する（サーバー起動なし） |
| 配置 | `tests/` 以下にソース構成をミラーする（`tests/aozora.test.ts`, `tests/api/search.test.ts`, `tests/components/*.test.tsx` …） |
| npm scripts | `npm test` / `npm run test:watch` / `npm run test:coverage` |
| CI | `build-and-test` ジョブに `npm test` を追加。既存の 50 作品 E2E スモークは残したうえで、実データの索引に注記・凡例が混入していないことの確認を1ステップ追加 |

### 追加した依存

`vitest`, `@vitest/coverage-v8`, `jsdom`, `@testing-library/react`, `@testing-library/user-event`,
`@testing-library/jest-dom`（すべて devDependencies）。JSX は Vite 内蔵の esbuild が
`tsconfig.json` の `jsx: react-jsx` を見て変換するため、React プラグインは不要でした。

### テストのために行ったリファクタ

| # | 内容 | 理由 |
|---|---|---|
| R-1 | `scripts/build-index.ts` の純粋関数（`textUrlFromFileUrl` / `parseCatalog` / `decodeText` / `pMap`）を `scripts/catalog.ts` に切り出して export。再試行は遅延を差し替えられる汎用の `withRetry` に変更 | `build-index.ts` は import しただけで `main()` が走るため、import してテストできない |
| R-2 | `tsconfig.json` の `exclude` から `scripts` を外す（`backend` / `frontend` は既に存在しないので削除） | `tsc --noEmit` が `scripts/` を型チェックしていなかった。テスト対象なのに型検査外なのは危険 |
| R-3 | `tests/` を `tsconfig.json` の型チェック対象に含める | テストコード自身の型崩れを CI で検知する |

## 9. 設計判断の記録

採否を確認したうえで対応した項目です。D-1〜D-3 は索引の中身が変わるため、**本番 DB の再インデックスが必要**です（D-8）。

| # | 論点 | 修正前 | 対応 | 影響 |
|---|---|---|---|---|
| D-1 | 凡例ブロックの索引混入（AZ-02, AZ-20） | 罫線1本目で切るため `【テキスト中に現れる記号について】` の凡例が本文として索引される | **採用**。罫線の間に凡例見出しがあれば2本目まで削る。無ければ従来どおり1本目で切る | **要再インデックス**。検索ノイズが減る |
| D-2 | 全角の入力者注が残留（AZ-13/14/16） | 半角 `[#…]` しか除去せず、実データの全角 `［＃…］` が素通り。『こころ』では 580 中 123 チャンクが汚染 | **採用**。全角 `［＃…］` `※［＃…］` も除去する | **要再インデックス**。「中見出し」「傍点」等での誤ヒットが消える |
| D-3 | 文末記号のない長大段落（CH-08） | 400文字上限を超えたまま1チャンクになる | **採用**。上限で強制的に切る | 要再インデックス。カードの表示崩れを防ぐ |
| D-4 | `limit` / `offset` が非数値（API-09/10） | `NaN` が DB 層まで届き **500** になる | **採用**。既定値（20 / 0）にフォールバックして 200 | 挙動改善のみ。再インデックス不要 |
| D-5 | `/api/stats` の障害隠蔽（API-22） | 例外を握り潰して 200 + `{0,0}` | **採用**。500 を返し、`page.tsx` は `res.ok` を見て件数表示を省く | 画面表示は変わらない。監視から障害が見えるようになる |
| D-6 | `snippet` の HTML エスケープ（UI-31） | FTS の生出力を `dangerouslySetInnerHTML` に渡す | **見送り**。実施するならインデックス投入時に `<` `&` をエスケープするか、描画時に `<mark>` 以外を無害化する | 未対応。描画時対応なら再インデックス不要 |
| D-7 | `scripts/` の型チェック除外（R-2） | `tsconfig.json` が `scripts` を除外し、インデクサが型検査されていない | **採用**。除外を解除（`tests/` も型チェック対象） | 解除後も既存の型エラーはなし |
| D-8 | 再インデックスの扱い | — | **未実施**。D-1〜D-3 の効果を本番に反映するには `npm run index` の再実行と Turso への取り込みが必要（全件 20〜60分） | 実行タイミングの判断が必要 |
